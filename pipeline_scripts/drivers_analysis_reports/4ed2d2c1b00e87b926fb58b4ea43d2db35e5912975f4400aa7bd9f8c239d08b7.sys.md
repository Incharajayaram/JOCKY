## 🔓 Attack Surface

### Device Names
```
Device Name:     \Device\rtkio
Symbolic Link:   \DosDevices\rtkio
```

Friendly, predictable name. From user mode:
```cpp
CreateFile("\\\\.\\rtkio", ...)
```

### Key Flag: `device_on_load_path = False`

The device is **not created when the driver first loads**. It requires an initialisation sequence (likely triggered by the Realtek user-mode utility). Your exploit would need to either replicate that initialisation or find an IOCTL that creates the device on demand.

### Device Creation API: `IoDevObjCreateDeviceSecure`

Unlike the standard `IoCreateDevice`, this driver uses the secure variant that allows attaching a security descriptor. Combined with the DACL manipulation imports, this strongly suggests the driver **sets an explicit DACL** on its device. The DACL may restrict access to administrators or SYSTEM only, which would make exploitation require prior privilege escalation.

## ⚠️ The 3 HIGH Severity Findings

### All 3 are `MmMapIoSpace` with User-Controlled Parameters

**Locations:** Lines 136, 698, 921

**Finding text (repeated 3 times):**
```
MmMapIoSpace called with parameters derived from user input.
This can allow a user-mode attacker to map arbitrary physical memory
into kernel virtual space, bypassing all protections.
```

**What this means:**
Three separate IOCTL handlers pass user-supplied physical address and size to `MmMapIoSpace`. Your user-mode code can request mapping of **any physical address** into kernel space.

**No `RtlCopyMemory` findings.** This is a pure hardware-access driver, not a buffer overflow target. The three `MmMapIoSpace` instances provide redundancy in case one handler has hidden validation.
